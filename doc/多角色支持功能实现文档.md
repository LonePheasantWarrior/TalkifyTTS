## 1. 目标与边界

Talkify 是 Android 系统 TTS 桥接应用，主要为第三方阅读软件提供朗读。本功能在**本地**依据用户配置的台词符号、人物名称和别名，将一段原文分为旁白与台词，并尽可能将台词分配给明确的角色音色。它不调用大模型，也不引入人物识别模型或额外的文本分析服务。使用云端 TTS 时，分段文本仍会按用户现有的供应商配置发送给相应 TTS 服务，可能产生原有费用。

**产品承诺：尽力识别明确的说话线索；没有足够证据或线索冲突时，使用「默认角色」音色，继续完整朗读。** 无法承诺任意小说都能准确分配每句话；第一版不推断代词、说话顺序、性别或跨段身份，也不根据人物被提及就断言其在说话。

阅读软件通常按段落提交文本，有利于匹配；但系统 API 不保证每次请求是完整段落，也不提供可靠的书籍 ID、章节位置或连续阅读会话。第一版每个请求独立解析，不把上一请求的引号或角色状态带入下一请求。跳章、重播、多阅读器交错不会污染归属。

### 1.1 第一版交付范围

1. 总开关默认关闭；关闭时保持当前单音色的外部行为和用户配置兼容。为满足 Android 回调线程契约，共享交付内部可以重构，但须覆盖单音色回归。
2. 多个可手动切换的「角色方案」：例如为不同小说准备方案；同一时刻只有一个生效。方案可重命名、复制、删除；不自动识别书籍。
3. 一个方案绑定**一个 TTS 供应商**：旁白、默认角色及所有人物从该供应商选择音色；账号、模型、接口、风格等沿用该供应商现有配置，用户无需重复填写凭据。创建时默认选主界面当前供应商，可在创建时改选；已创建方案的供应商不可直接修改，需复制成新方案并重新选择音色。多角色启用时使用方案绑定的供应商，不依赖主界面选中的其他供应商。主界面切换供应商不改写方案；页面明确显示当前生效供应商。此约束避免第一版把混合供应商、音频重采样和复杂的资源生命周期一起引入。
4. 每个方案必须有且仅有一个**旁白**和一个不可删除的**默认角色**，各自选择音色；允许添加多个具名角色、别名与音色。不同角色允许选择相同音色。默认角色不是人物，不参与名称匹配。
5. 支持配置台词符号对：内置中文双引号 `“”`、直角引号 `「」`、英文双引号 `""`，首次新建默认启用上述三对；提供 `『』`、`【】` 等可选预设及自定义单 Unicode 码点符号对。符号规则见第 4 节。
6. 完成中文与英文的保守规则匹配、原文无损切分、顺序合成、试听、设置持久化、错误提示与测试。默认不插入人工静音，不新增风格指令/语速/音调覆盖；沿用系统请求和供应商原有设置。
7. 系统 TTS 与方案内试听使用同一个解析器和编排规则；各自音频输出适配不同，不能通过自调用系统 TTS 充当唯一测试。

**不在第一版实现：** 机器学习/AI、全书导入与预处理、书籍自动识别、角色自动发现或自动选声、跨请求上下文、角色性别推断、任意正则、跨供应商混合、重采样、原文标记语言、音频缓存及并发预取、朗读时弹窗纠错。架构可扩展，不为未来引入无实现的复杂框架。

### 1.2 能力示例

| 原文与配置 | 预期 |
|---|---|
| `张三说：“你先走。”`，配置张三 | 台词用张三；其余为旁白 |
| `“我不走。”李四说。`，配置李四 | 台词用李四 |
| `张三对李四说：“你先走。”`，配置二人 | 张三说话，不因李四离引号更近而错配 |
| `“我不走。”李四说，“我要留下。”` | 两句均可归李四，具体需满足第 4 节规则 |
| `张三说：“走吧。”李四答道：“好。”` | 第一台词张三、第二台词李四 |
| `“听我的。”` | 无明确线索，默认角色 |
| `他对张三说：“走吧。”` | 张三是受话人；默认角色 |
| `张三看了看李四：“走吧。”` | 缺少明确说话动词；默认角色 |
| `Alice said, "Go."`、`"Go," said Alice.` | 配置 Alice 时匹配 Alice；忽略英文大小写 |

示例展示目标，不代表规则可以理解所有文学表达。实现时使用第 4、5 节的精确规则和测试语料作为准绳；不通过额外的宽泛猜测让示例通过。

Android 官方要求 `onSynthesizeText` 同步完成，返回后不能再使用回调；`SynthesisCallback` 的 `start`、`audioAvailable`、`done`、`error` 等必须在 synthesis 线程调用，单次写入不得超过 `getMaxBufferSize()`：[TextToSpeechService](https://developer.android.com/reference/android/speech/tts/TextToSpeechService)、[SynthesisCallback](https://developer.android.com/reference/android/speech/tts/SynthesisCallback)。现有实现存在从供应商回调线程直接调用框架 callback 的路径；本功能应把该缺口作为共享交付层整改，而非复制旧写法。不得把测试通过视作线程契约已满足。

## 3. 产品模型与状态

示意模型，具体 Kotlin 名称可调整，但语义不可改变：

```kotlin
data class MultiRoleSettings(
    val enabled: Boolean = false,
    val activeProfileId: ProfileId? = null,
    val profiles: List<ReadingProfile> = emptyList(),
)
data class ReadingProfile(
    val id: ProfileId,
    val name: String,
    val providerId: String,
    val narratorVoice: VoiceRef?,
    val defaultRoleVoice: VoiceRef?,
    val roles: List<Role>,
    val delimiters: List<DelimiterPair>,
)
data class Role(val id: RoleId, val name: String, val aliases: List<String>, val voice: VoiceRef?)
data class VoiceRef(val voiceId: String) // 名称仅用于展示时可缓存，不参与身份判定
data class DelimiterPair(val open: Int, val close: Int, val enabled: Boolean) // Unicode 码点
```

- `ProfileId`/`RoleId` 使用稳定随机 ID；不要用数组下标、名称或时间戳当身份。方案与角色重命名不影响绑定。
- 全局开关初始关闭；没有有效方案时不能启用。方案编辑可保存草稿，但启用必须通过校验。删除生效方案时先明确说明并在同一次原子变更中关闭多角色和清空 active ID；不自动选择另一方案。
- 启用状态下，切换方案或提交当前方案编辑前先验证目标方案；如未通过，保留上一个有效方案并就地显示原因。编辑草稿独立于已生效配置，取消不影响朗读；如需保存不完整草稿，先关闭多角色或保存为非当前方案。供应商被外部改配置、模型被删除等不可控变化导致已保存方案失效时，不擅自修改用户配置，运行时按第 7 节回退并显示「需要修复」；修复后基于最新配置重新校验。
- 校验：方案名非空且在本地唯一；角色名称、别名 trim 后非空；同一方案中名称及别名按匹配规范归一化后全局唯一，同角色内也不允许重复。旁白、默认角色、所有具名角色均有有效音色；至少启用一对有效符号；绑定供应商已注册且配置就绪、音色仍可用且音频格式兼容（第 7 节）。不允许以名称 `旁白`/`默认角色` 创建具名角色，避免 UI 歧义。
- 资源上限：最多 20 个方案、每方案 100 个具名角色、每角色 10 个别名、每个名称或别名最多 40 个 Unicode 码点、最多 16 对启用符号。超过上限应在编辑时提示；加载旧数据也要有界校验。可根据后续性能数据调整，但修改时同步更新测试和文案。
- 匹配归一化：去两端 Unicode 空白，ASCII 英文字母按一对一小写转换比较；其他字符逐码点精确比较。词典查重与文本匹配使用同一算法；不对原文使用会改变长度的整体大小写转换、Unicode 兼容归一化或拼音匹配，始终保留原始 UTF-16 偏移。中文不做繁简自动转换；用户可添加别名。
- 音色选择只存稳定 ID；不能把音色显示名当 ID。角色音色只是请求级选择，不修改全局供应商配置或写回全局主音色。

## 4. 解析器：数据不变量与符号处理

### 4.1 分层与中间结果

解析模块是纯 Kotlin、无 Android 和 I/O 的领域逻辑，可注入字典和参数。区分：

1. `QuoteScanner`：在原始文本上寻找**最外层**完整台词符号对，生成旁白、台词的有序原文区间；支持嵌套，详细规则见下。
2. `AttributionEvidenceExtractor`：只分析台词外的相邻旁白片段，提取带原始区间、关联方向、角色 ID、规则类型的可解释证据。
3. `RoleAttributor`：按第 5 节确定性规则归属，得到角色或默认角色；不会改变任何原文。
4. `SpeechPlanBuilder`：得到 `SpeechSegment(start, endExclusive, kind, roleId?, voiceRef)`；区间采用 Kotlin/Android 原始 UTF-16 偏移。角色表、符号及供应商配置在请求开始时取**不可变快照**。

核心不变量：有序区间覆盖 `[0, text.length)`、相邻无缝、不重叠、不重复；对每个区间使用 `text.substring(start, endExclusive)` 按顺序拼接须**逐 UTF-16 单元等于原文**。不得因 trim、过滤纯标点、引号、空格、换行、emoji 或 `<<...>>` 模式而删改文本；引号交给 TTS 供应商原样处理，不承诺供应商一定读出符号名。`Span` 位于合法 UTF-16 边界，不能切断代理对。多角色解析器和编排器传给 Provider 的区间不得改写；供应商内部已有的分块或协议要求可能另做规范化，不可将计划无损夸大为对远端发音或逐字节报文的保证。审计供应商分块行为，发现会丢失实质内容时作为缺陷修复。

纯空白/标点区间仍保存在计划里：如果供应商不会单独合成该区间，将其按顺序附着到相邻可发声区间（优先附着左侧；无左侧则附右侧），保留每个源字符一次。整次请求没有可发声文本时，按原服务契约处理，不要伪造音频或误判成功。限制请求长度以 Android 调用实际输入和既有保护为准；过大或超出解析资源预算时，整次使用旁白音色合成**完整原文**，不得截断。

纯数字台词与旁白是可朗读内容，不属于应附着或忽略的纯标点：例如 `张三说：“123。”` 中的数字应使用张三音色发出。当前 `AbstractTtsProvider.containsReadableText` 只检查 UTF-16 字符是否为字母，会拦截纯数字和部分补充平面文字；实现时修正共享判定为按 Unicode 码点识别字母或数字，并核查各供应商自己是否另有过滤。若某供应商不能处理该文本，要显式返回错误，不得以零音频完成而继续下一段。此项是已知既有缺陷的必要修正，需同时做普通单音色回归。

### 4.2 符号对与异常

- 自定义开/闭各一个 Unicode 码点；允许开闭相同（如英文 `"`），不允许空白、字母、数字、控制字符、代理项、换行或同一个开符对应多个闭符。所有启用符号的字符必须互不冲突；同一对开闭相同除外。UI 校验并解释，不使用用户正则。
- 使用栈遍历码点，开闭不同的符号按配对匹配；允许不同对嵌套，最外层是唯一台词区间，内层符号不产生新角色切换。开闭相同的符号在同类栈顶时闭合，否则开启；同类对称符号不支持自嵌套。转义语法第一版不特判，符号本身原样保留。
- 多余闭符作为普通原文；最外层未闭合时，从其开符起至本请求结尾统一作为**旁白**，不从中提取人物，也不能把这一尾部当作前一台词的后置证据；之前完整台词仍正常处理。可预览提示「有未闭合符号，本次剩余文本按旁白处理」。默认 `"` 属于对称符号，孤立的 `"` 无法区分开闭，按未闭合处理。
- 开闭之间没有可发声内容时仍保留原区间及符号，交给计划构建阶段附着；不生成无意义的单独供应商调用。
- 台词符号内容仍保留首尾标点；引用、书名、反语也可能被当作台词，应在 UI 里解释可通过调整符号缓解，而非宣称能识别真实对白。
- 对恶意输入设上限：单请求最多 4096 个最外层台词区间、嵌套深度 32、候选证据最多 4096 条；超限整请求退回旁白原文。限制值为实现硬上限，不是对外能力宣传；测试最坏情况与取消响应。

## 5. 人物归属算法：证据优先，冲突回退

### 5.1 输入与搜索范围

令每两个相邻最外层台词之间的旁白为一个 `gap`；台词前后边缘也视为 gap。证据只来自紧邻目标台词的 gap；绝不穿越另一个台词。gap 中中文 `。！？；`、英文 `. ! ? ;`、换行及其全角形式作为强边界；逗号、顿号、冒号是弱边界。英文小数点、缩写和复杂标点在第一版不做语义理解，无法判定时宁可回退。**台词内部的句号不阻止紧邻闭引号后的后置说话标签**。

对台词左侧，取紧邻开引号的最后一个强边界后的片段；右侧，取紧邻闭引号后的第一个强边界前的片段。强边界自身保留在原文区间中，但不计入候选窗口；判断是否到达句末时可检查窗口外紧邻的边界字符。每侧最多扫描 80 个 Unicode 码点，超过时从靠近台词的一侧取窗口；窗口以码点边界截取，人工截断处不得视为真实词界，只有能证明标签完整才可使用。若 gap 中有多个分句，不得跨强边界寻找名称或动词。相邻 gap 分别分析并在所有台词之间统一分配归属，不能各台词独立搜索后互相争抢同一证据。

例如 `“走。”张三说。李四说：“好。”`：中间 gap 被句号分开，左片段只为第一句提供张三的后置证据，右片段只为第二句提供李四的前置证据。一个 gap 包含强边界时不使用两句共享规则；若无强边界，才按第 5.3 节共同分析该 gap。

### 5.2 词典、词界与基本语法

预先编译角色名及别名为字面量匹配器，按最长词优先解决同位置前缀重叠；同一个位置存在多个不同角色的同长候选时视为冲突。ASCII 英文字母大小写无关，其他字符精确匹配；英文/数字/下划线的名称前后不得与英文/数字/下划线相接。中文不可只凭子串命中：名称必须出现在下述**受支持的说话标签语法位置**，且其前只能是真实窗口起点、空白、标点、引号边界或明确的连接词 `然后`、`接着`、`但`、`而`；不支持的上下文一律默认，避免把 `张三` 从 `张三丰`、`老张三` 中截出来。单字中文名称可配置，但同样受此限制，容易歧义时建议添加更完整别名。

第一版把说话动词维护为代码内、版本化的有限集合，不开放任意正则：

- 中文：`说`、`说道`、`道`、`问`、`问道`、`答`、`答道`、`回答`、`喊`、`喊道`、`叫道`、`低声说`、`轻声说`、`笑道`、`叹道`、`叫`。最长动词优先。
- 英文：`said`、`says`、`asked`、`asks`、`replied`、`replies`、`answered`、`answers`、`whispered`、`shouted`，大小写无关，遵守英文词界。
- 中文证据支持 `角色 + 说话动词`，以及 `角色 + 对/向 + 另一个已配置角色 + 说话动词`；后者前一个角色为说话人。英文支持 `角色 + 动词` 和 `动词 + 角色`，两者之间至少一个空白字符。名称、动词与连接结构之间只允许空白；不在证据内使用通配符、任意插入动作描述或不受控回溯正则。`角色 + 对/向 + 角色 + 动词` 必须作为整体优先匹配，不能另把受话人和动词抽成独立证据。
- 只识别完整标签。没说话动词的人名、代词、独立的 `角色 + 冒号`、别名出现在引号内、名字作为受话人而主语是代词，均不构成说话人证据。匹配器要记录证据在 gap 中的原始范围、说话人、连接标点及可归属方向。检测不支持的更长主语或相邻人物时宁可弃用证据。

这个语法刻意有限；后续扩展词典或语法时要加入对照语料和误判测试。不要用宽泛的 `contains(name)`、任意窗口内人名最近、或单纯评分冒充语义分析。

### 5.3 前后归属与裁决

先整体解析 gap 中的标签及其标点，再将证据绑定左侧台词、右侧台词或两者：

1. **前置标签**：标签后到右侧开引号之间仅有空白和至多一个冒号 `:`/`：` 或逗号 `,`/`，`，标记为右侧候选；段落边缘的逗号覆盖 `Alice said, "Go."`。位于两段台词间时，必须先按第 3 条判断，不能单独套用本条。冒号是明确的右向信号。
2. **后置标签**：左侧闭引号到标签前仅有空白、逗号或顿号，且标签后到强边界/段落末仅有空白及句末标点，归左侧；这覆盖 `“好。”李四说。`、`"Go," said Alice.`。
3. **夹在两句之间且 gap 无强边界**：`左台词 + 标签 + 冒号 + 右台词` 只归右侧；`左台词 + 标签 + 逗号/顿号 + 右台词` 可同时归两侧（中断说话标签）；标签后无标点直接接右引号或标点结构不明确时，不将该证据用于任一侧。此处逗号连接只是约定俗成的启发式，不保证真实说话人一定相同。额外文本、多个标签或多个说话人使结构不满足上述形式时，不使用该 gap 的含糊证据。若 gap 有强边界，按 5.1 分别处理其左右边缘，不能把另一侧的标签当冲突或整段丢弃。
4. 对一条台词，汇总来自左右两侧的**有效**证据：角色唯一则采用；多个证据指向同一角色仍可采用；不同角色则使用默认角色，不凭距离或用户角色顺序决胜。没有证据亦用默认角色。前置例外必须由上述方向规则先消除，而不是静默覆盖冲突。
5. 仅限一个台词时，段落边缘的标签也按同样语法处理。无引号的整段按旁白，第一版不猜测无引号对话。

实现前先写表驱动测试验证第 1.2、10.1 节的全部期望。对 `张三说：“走吧。”李四答道：“好。”`，`张三说：` 是第一台词的左证据；中间 `李四答道：` 是第二台词的右向前置证据，不能归第一句。对于 `“我不走。”李四说，“我要留下。”`，中间标签以逗号连接，可归两句。对于 `张三说：“走。”李四说。`，第一句的左右证据不同，必须回退默认角色。

### 5.4 复杂度与安全

扫描符号为 O(n)；角色词典使用有界前缀树或等价的多模式字面量匹配器，避免逐角色对整个长文本反复正则搜索；只对有界 gap 窗口提取证据。常数、上限与内存使用需通过最大配置及超长输入压测，禁止灾难性回溯正则。解析结果的调试理由只在本地预览中按需生成；日志、通知和遥测不得包含原文、人物名、别名或配置文本。

```text
Compose 页面 / ViewModel ──> MultiRoleRepository ──> 原子版本化存储
          │                             │
          └─ 预览编辑 ─> 同一 Parser     └─ 请求开始读取不可变快照
                                      │
Android SynthesisRequest ─> 请求协调器 ─> Parser ─> SpeechPlan
                                                └─> 顺序语音执行器 ─> PCM 交付适配器
预览播放器 ───────────────────────────────────────┘         └─> AudioOutput
```

推荐代码位置：

- `domain/model/multirole/`：方案、角色、校验错误、区间/计划；`domain/repository/MultiRoleRepository.kt`：原子读取与修改接口。
- `domain/multirole/`：纯 Kotlin 词典、扫描、证据与裁决、计划构建；与 UI、供应商协议无依赖。
- `infrastructure/app/repo/`：版本化序列化与存储；供应商能力适配放现有 `service/provider/` 而不反向依赖 UI。
- `service/`：可测试的请求会话协调器、计划执行器、框架交付桥；`TalkifyTtsService` 只保留生命周期和平台适配；预览复用相同计划与执行器但拥有独立会话/供应商生命周期。
- `ui/screens/`、`ui/components/`、`ui/viewmodel/`：页面、音色选择和状态管理。文件名可依工程风格调整，不为每个数据类单独建文件。

**持久化方案：** 为这组需要事务及失败反馈的结构化数据单独引入稳定版 Preferences DataStore，经领域仓储隔离；不迁移现有应用及供应商的 SharedPreferences。将整个版本化配置作为单个 JSON 字符串保存在 `files/datastore/talkify_multirole.preferences_pb`，通过 `edit { ... }` 在同一事务内基于当前值做读改写；限制编码后最大 1 MiB，超限拒绝保存并给出提示。序列化、校验与 I/O 不在主线程；禁止“UI 读旧快照 → 并发覆盖全量”。所有调用方共用应用级唯一 DataStore 实例，不在多个仓储实例中各自创建；DataStore 不可再叠一份自行维护的持久状态缓存。当前 manifest 的 Activity 和 Service 均未指定独立进程，按单进程设计；若未来改变进程模型，必须先迁移到适用的跨进程存储，不得混用单进程与多进程 DataStore。[DataStore 契约](https://developer.android.com/reference/kotlin/androidx/datastore/core/DataStore)规定更新在持久化后完成、失败抛异常；UI 只在事务成功后显示已生效，失败时保留原配置并提示。请求读取 `data.first()` 的不可变快照，切换/编辑只影响**下一次请求**。

- schema 带版本号；缺字段使用安全默认值，未知未来版本不得覆盖原数据。损坏时保留原文件，关闭多角色、保留原单音色能力，向用户提示修复；禁止默默重置并写回空配置。提供可测试的升级迁移。
- 方案及别名可能包含用户的阅读偏好；按隐私优先，第一版从云备份和设备迁移均排除实际 DataStore 文件：在 API <31 的 `backup_rules.xml` 及 API 31+ 的 `data_extraction_rules.xml` 的 cloud-backup / device-transfer 中添加 `domain="file" path="datastore/talkify_multirole.preferences_pb"` 排除项。实现时核对实际文件路径并验证规则；不复制或存储供应商凭据，既有排除规则不变。页面帮助中说明换机后需要重新设置。
- 除用户手动配置的方案名称/角色名称外，不持久化阅读文本、匹配记录或试听输入；不得上报角色名、别名、原文、书名、声音自定义值。保留现有遥测许可/数据模型，不新增会透出文本的事件。检查现有 debug 路径：`TalkifyTtsService.onSynthesizeText` 当前会记录整段请求；新实现必须移除原文日志并审计相关供应商、异常和预览回调，不把上游错误正文当成安全日志或通知。
- UI 读取使用 `collectAsStateWithLifecycle()`；配置输入草稿用 `rememberSaveable` 或 ViewModel 处理旋转及导航，不保存网络请求结果。试听原文仅保存在内存，允许旋转时由 ViewModel 暂存，但不写入 `SavedStateHandle`、`rememberSaveable` 或其他持久存储，进程销毁后丢弃。不要在 Compose 组合期做磁盘或音色解析 I/O。

## 7. 合成、音频与失败契约

### 7.1 请求入口与音色覆盖

- 开关关闭、没有有效方案或设置不可读时不经过多角色执行器；正常单音色行为、系统语言/语速/音调和已有设置保持兼容。设置损坏、配置变化或供应商不兼容时明确提示并回退普通单音色；普通供应商也不可用时按既有错误处理。通知应去重，避免连续段落刷屏。
- 启用且方案有效时，**先选方案绑定的供应商再校验它**，不可先要求主界面当前供应商可用。验证每个将实际使用的角色音色、供应商凭据、模型和音频能力；在方案中音色已明确给出的情况下，不能额外要求供应商配置中普通单音色的 `voiceId` 非空，但凭据、模型和供应商特定约束仍须满足；需要调整的供应商分别测试。不要泄露凭据。编辑中方案变无效应禁止重新启用并给出修复入口，当前请求仍使用开始时的快照。
- **系统发现与合成的一致性**：抽出一个共享的生效配置解析器，供服务的语言/音色发现（`onIsLanguageAvailable`、`onLoadLanguage`、`onGetLanguage`、`onGetVoices`、`onGetDefaultVoiceNameFor`、`onIsValidVoiceName`、`onLoadVoice`）、`TalkifyCheckDataActivity` 和请求入口使用同一决策：开启且方案有效时使用方案供应商，否则使用主界面普通供应商。尤其要覆盖首页选了未配置供应商、方案供应商已配置的情况，不能让数据检查错误地隐藏 Talkify。检查语言、音色及本地模型就绪状态使用当前生效配置，而不是各入口各自选择供应商。同步 Android 入口读取配置须确保有界，不能在主线程等待网络/下载，且不能为规避读取维护另一份自行失效的 DataStore 缓存；读取失败使用同一明确的回退决策。系统请求中的语言/语速/音调继续传递；启用多角色时由方案音色控制角色，系统 `voiceName` 不再覆盖这些音色，应在帮助中说明。关闭多角色时保留既有语义。
- 方案切换和普通/多角色开关可能改变系统公布的音色和语言；部分客户端可能缓存旧列表或旧 voice 名称，不能保证立即刷新。提示用户必要时在阅读软件中重新选择 Talkify 或重启其 TTS 会话；跨供应商旧 `voiceName` 不得导致角色声音错用。配置快照按请求固定；并发的系统发现/切换不得释放正在合成的 Provider：使用带会话租约的资源所有权或等效串行生命周期机制，在在途引用结束后释放，并覆盖切换、停止和服务销毁的交错。
- 在 `SynthesisParams` 中增加明确的 `voiceOverride: String?`（或等价请求级值对象）：`null` 表示既有正常单音色解析逻辑；非空表示本段指定声音，不能读取或修改持久配置。每个供应商真实请求构建点均须尊重覆盖，按各自格式解析。OpenAI 的 `customVoiceId` 目前优先于配置音色：多角色的明确覆盖必须优先于它，而普通单音色仍维持原优先级；请求日志/遥测的有效音色语义也要同步修正。小米语言映射、腾讯音色采样率、本地模型音色目录等均应实际核对，不因改了公共参数就宣称已支持所有供应商。
- 增加可查询的供应商能力：对具体**配置 + 音色**返回可靠的输出 PCM 格式（采样率、编码、声道）及该音色可否请求级覆盖；未知即 `Unknown`，禁止把 `getAudioConfig()` 的默认值当作某个具体音色的保证。所有本次计划中会使用的音色必须已知且格式完全一致才能启动多角色；UI 在选择/启用时给出可操作的限制。腾讯按目标音色实际采样率判断；本地按选中模型判断；Azure/MP3 的实际解码格式需验证。格式不可预知的供应商先标记不支持多角色并说明原因，完成能力适配与测试后再启用，不能因为目标是支持九家而虚报支持。
- 哪怕预检通过，也必须对每个音频 chunk 检查实际 `(sampleRate, encoding, channels)` 是否与已启动流完全一致；不一致立即停止并报告合成失败，不能把不同格式 PCM 当同一格式播放。第一版不做重采样；UI 不允许选择不兼容音色。运行时冲突可能在部分音频交付后才发现，此时不能重播整段或静默切回旁白。

### 7.2 顺序、交付和取消

- 为一个外部请求建立唯一 request generation 和结构化取消作用域，覆盖配置读取、解析、供应商启动、段间空隙、音频写入及所有清理。`onStop`/销毁/超时将该请求原子作废，取消在途供应商，释放阻塞队列；作废后不得启动下一段或发起新的音频写入。已进入框架的阻塞调用可能与取消并发，不能承诺撤回已经交付或正在交付的数据；完成后必须检查作废状态再处理任何事件，且不让停止操作死锁等待持锁写入。旧回调必须受 request generation **和段 generation** 防护，不能仅靠一个可覆盖的 `activeContinuation` 指针。
- 同一方案请求按原文顺序串行合成；相邻且声音相同的区间在不改变字符顺序的前提下合并，减少调用；不得跨其他角色合并。首版无段间额外静音与并行预取。供应商自身已有的分块流水线可沿用，不得破坏其有界背压与取消。
- 供应商回调线程只把音频/终态作为有界事件交给请求协调器；由 `onSynthesizeText` 所在线程消费事件，串行调用 `SynthesisCallback`。若 `synthesize()` 可能同步回调或阻塞，必须从可取消的工作线程启动生产者，不能先在合成线程等待生产者返回再消费有界队列，否则会死锁。队列按字节数和事件数同时有界；消费者慢时要有背压，生产者不得在持有会阻碍 `stop()` 的供应商锁时无限等待；取消时唤醒双方。研究各供应商回调能否阻塞，不能安全阻塞者需有界桥接与明确溢出失败；不得无界缓存整段音频。
- 每次外部请求最多 `start` 一次，内部结果恰好决定一次；流格式从首个实际 PCM 确立并与预检一致。音频按帧对齐且每次写入长度 `<= callback.maxBufferSize`；遇到 `STOPPED`/`ERROR` 立即停止供应商和后续段。首次音频前失败可以直接报错；已经交付部分音频后失败只报告失败，不重放已交付部分。在 synthesis 线程以明确状态机按照 Android 契约结束：普通失败先 `error()`，结束时调用 `done()`，成功也调用 `done()`，不得在 `done()` 后补报错误；`done()` 最多调用一次。取消/STOPPED 的具体返回和通知须用真实框架验证。任何回调不得发生在 `onSynthesizeText` 返回之后。
- 120 秒是**整次请求**的上限，覆盖解析和全部段的合成，不是每段各 120 秒；沿用现有唤醒锁、WifiLock、前台服务空闲退出和错误上报，清理恰好一次。不能吞掉 `CancellationException`。服务/预览销毁需释放各自的供应商；不要从通用工厂无目的创建临时 Provider 后不释放。
- 已开始输出后某段失败、零音频、格式冲突、框架拒收均不得标记成功；带结构化错误码但不暴露隐私内容。按现有 `TtsTelemetryTracker` 合理记录一次请求的终态；多角色不能把每段完成误报为整个请求完成，元信息不能伪装成其他供应商。多角色维度若现有 schema 无法准确表达，应先设计并测试 schema，不上报编造值。

### 7.3 性能与实际成本

解析是本地轻量 CPU 工作；音频则可能因为台词切换而产生多次 TTS 请求，每段首包延迟和云服务计费规则由供应商决定，可能导致停顿或费用变化。界面帮助应明确说明。验收记录真实设备从请求到首音、段间停顿、停止响应及供应商调用数；应与现有单音色基线对照，先测量再决定优化，不能以无界预取掩盖延迟。

## 8. UI 与交互规范

### 8.1 设计方向

遵循现有 Compose + Material 3 主题、动态配色、深浅色和 edge-to-edge，采用与项目一致的排版、色彩与动效。参考 Android 官方 [Material 3 与 Expressive](https://developer.android.com/develop/ui/compose/designsystems/material3)、[自适应布局](https://developer.android.com/develop/ui/compose/layouts/adaptive/support-different-display-sizes)、[Compose 无障碍语义](https://developer.android.com/develop/ui/compose/accessibility/semantics)。实现时检查稳定版/BOM 与现有依赖兼容；适度采用稳定的 Material 3 Expressive 组件或动效，不能为一个页面强行升级到预发布依赖或重写全应用主题。2026-11-04 官方版本页列出的 Material 3 稳定版为 1.4.0、1.5.0 为 RC；实际实现以当时官方版本与项目 BOM 为准，不硬编码过时结论。

视觉原则：信息层次清楚、内容优先；用一致的列表项与分组，减少大面积嵌套卡片。人物使用字母/汉字首字或简洁图标即可，不生成虚构头像；不要用性别、颜色或图标暗示真实角色属性。将复杂解释放在「如何匹配」与文本预览，不把技术术语或长篇规则堆在首屏。

### 8.2 入口与主页面

沿用 `MainScreen` 已有的右下角 `Scaffold.floatingActionButton`：在原有「供应商设置」浮动按钮**旁边**增加一个独立的「多角色设置」按钮，二者在同一行对齐、保持适当间距；原按钮继续打开原有供应商设置抽屉，新按钮直接进入多角色独立页面。原按钮位置和点击行为保持可预期；以右向左界面为逻辑镜像。使用与现有 Material 3 风格一致的容器、形状和图标，区分“供应商设置”和“多角色设置”的图义；不要给两个按钮都使用齿轮。两个按钮均有明确的本地化无障碍名称、至少 48dp 可操作区域及键盘焦点；不要只依赖图标或颜色表达功能。

为保持首页整洁，不新增常驻卡片、不使用自动展开的按钮菜单。多角色按钮在开启时可用简洁状态标记辅助识别，并在语义中读出「多角色朗读已开启/已关闭」；加载和设置损坏时使用可区分的状态，不要误报关闭或开启。进入设置页后展示当前方案和生效供应商。主界面当前显示的是普通供应商与普通音色；只要多角色启用，就在不遮挡内容的位置展示简短提示「多角色使用：方案名 · 供应商」，帮助用户理解首页普通音色不会覆盖方案音色；无须展示角色名或台词。首页试听保持现有普通音色语义，并明确标识「单音色试听」；多角色试听在多角色页面进行。点击按钮不会直接开启功能。

适配 IME、系统导航栏和横竖屏/分屏：利用 Scaffold 的窗口内边距，在滚动内容末尾预留足够空间，使最后一项可完全滚动到按钮上方；Snackbar 与按钮避免遮挡。窄屏、大字体或按钮空间不足时保持两项可达且触摸区不重叠，不以缩小到 48dp 以下作为兜底；通过布局切换保持入口靠近右下角，不改变两按钮各自功能。

### 8.3 首次设置和方案管理

首次打开提供简洁说明和「创建方案」。创建流程：输入方案名 → 选择已配置供应商（默认主界面当前项，允许去供应商设置）→ 选旁白及默认角色音色 → 选择台词符号 → 完成；具名角色可稍后添加。任一项无效时显示具体原因，不进入虚假的已开启状态。首次完成后由用户明确开启开关。

方案切换列表显示名称、供应商、角色数量及当前状态；支持创建、复制、重命名、删除。复制保留角色与符号，生成新的内部 ID，用户可选择新供应商；若新供应商不同，保留角色文本但清空所有音色并标记待配置，不自动映射不同供应商的同名音色。删除给出清晰确认；删除当前方案会同时关闭功能。切换方案无重启，下一请求生效；正在播放的请求保持旧快照。

### 8.4 角色、音色和符号编辑

- 角色列表固定置顶「旁白」「默认角色」，解释默认角色用于未识别台词；二者不可删除或重命名。添加角色页面包含名称、可选多个别名、音色；保存前就地标明重复名称/别名或缺项。删除普通角色需确认并说明其台词以后可能使用默认角色。
- 音色选择复用现有 `VoiceRepository`、项目音色分组与试听设计，加入搜索、已选状态和加载/失败/无可用音色反馈；显示供应商/实际音色名。对于现有 OpenAI 兼容供应商配置中的自定义音色 ID，音色列表应提供明确的「当前自定义音色」候选；其可用性/格式无法确认时按能力规则提示，不能假装选中的预置声音实际生效。第一版不承诺为每个角色单独输入任意自定义 ID。明确展示不可用或输出格式不兼容原因及修复操作。试听使用该角色实际音色、相同供应商配置，停止/切换试听可立即中断；预览失败有可理解的错误，不泄露密钥。
- 台词符号页面展示预设开关、实际样例及自定义成对符号的开/闭输入；相同符号对、冲突、无效码点即时提示。`【】` 说明「某些作品中是系统提示」，由用户选择。至少保留一对启用符号。修改只影响当前方案。
- 「试一段文本」允许粘贴短文本或使用内置示例；点击分析后，用清晰的分段文本与文字标签显示「旁白」「张三」「默认角色」，并解释「未找到明确说话人」或「前后线索冲突」。辅助色只作补充，不作为唯一标识。提供「试听」和「停止」；分析与试听复用真实解析及执行路径，预览样本文本不持久化或上报。不要声称该预览能代表其他阅读器的所有切分方式。
- 「如何匹配」以真实例子解释前后说话标签、默认回退、符号误判、阅读软件按段切分差异、云 TTS 请求次数/费用及手动切换方案。不要暗示自动识别所有人物。

### 8.5 无障碍与反馈

按钮具备明确的内容描述、状态和语义；角色/符号选择可被 TalkBack、键盘和方向键操作，触摸目标至少 48dp；支持放大字体、浅色/深色、高对比、横屏和动画减弱。危险操作可取消，保存成功/失败有适当反馈。所有可见文案进入资源文件并保留本地化能力；不把人物原文放进 snackbar 或系统通知。对预览文本和角色设置不加入遥测采集。

## 9. 分阶段实施与交付门禁

这些阶段是一个完整功能的内部实施顺序，不代表只交付界面或只交付引号双音色就算完成。

1. **测试先行与规则**：建立人工标注的匿名/自编中文和英文段落语料，覆盖第 10 节；实现配置校验、纯 Kotlin 扫描、证据、裁决、完整性不变量及确定性测试。
2. **音色与交付基础**：引入请求级音色覆盖；逐供应商证明真实请求音色优先级、格式能力、预览一致性；重构共享的 callback 交付，使系统回调运行在 synthesis 线程，先证明单音色无回归。
3. **系统 TTS 编排**：单请求快照、串行计划、格式守卫、取消、超时、资源释放和终态，假供应商可控制回调、延迟、失败与格式；新增完整集成测试。
4. **设置与体验**：原子持久化、方案/人物/符号页面、试听与结果解释、无障碍、异常提示、备份排除；更新 `doc/开发指南.md` 和用户可见帮助。
5. **实机与发布**：完成第 10 节测试和实际阅读软件兼容验证，通过项目 CI、release R8 冒烟，再提交交付说明。无法实机验证某供应商或客户端时明确记录为未验证，不标记为已全部支持。

## 10. 验收与验证

### 10.1 必须覆盖的解析语料

用表驱动测试断言完整原文分区、每段角色、证据来源及默认回退。至少覆盖：

| 分类 | 输入 / 场景 | 期望 |
|---|---|---|
| 左、右 | `张三说：“你好。”`；`“你好。”张三说。` | 张三 |
| 双人受话 | `张三对李四说：“走。”` | 张三 |
| 主语不明 | `他对张三说：“走。”` | 默认角色 |
| 前后相邻 | `张三说：“走吧。”李四答道：“好。”` | 张三、李四 |
| 强边界分离 | `“走。”张三说。李四说：“好。”` | 张三、李四 |
| 中断台词 | `“我不走。”李四说，“我要留下。”` | 李四、李四 |
| 冲突 | `张三说：“走。”李四说。` | 默认角色 |
| 无线索 | `“听我的。”`；`张三看了看李四：“走吧。”` | 默认角色 |
| 指代 | `张三走过来。他说：“走。”` | 默认角色，不跨强边界推断 |
| 名称重叠 | 同时配置 `张三`、`张三丰`，`张三丰说：“走。”` | 张三丰，不误匹配张三 |
| 假子串 | 仅配置 `张三`，`老张三说：“走。”` | 默认角色 |
| 别名 | 配置张三别名三哥，`三哥说：“走。”` | 张三；重复别名保存被拒 |
| 英文 | `Alice said, "Go."`；`"Go," said Alice.` | Alice；`Malice said, "Go."` 不匹配 Alice |
| 数字及补充字符 | `张三说：“123。”`、Unicode 补充平面的文字 | 内容送达合成，不因现有字母过滤而静默跳过 |
| 符号 | `「他说：『快走』。」` | 仅外层一个台词，内文不另分角色 |
| 混杂 | 对称 `"`、中文括号、emoji、换行、纯标点、相邻台词、空引号 | 不丢字符；角色按规则或默认 |
| 畸形 | 多余闭引号、未闭合最外层、超过嵌套/数量上限 | 按第 4 节安全回退，原文完整 |
| 界限 | 80 码点窗口边界、中文/英文标点、超长标签、多个角色证据 | 不从半个证据猜角色；冲突回退 |
| 稳定 | 同一请求重复解析；角色配置列表换序 | 结果一致，不能以配置顺序消解歧义 |

补充性质测试/模糊测试：随机 Unicode、代理对、长重复符号、随机合法符号对与角色表；断言解析终止、区间不越界、拼接等于输入、没有非法 UTF-16 边界、受限制的运行时间与内存。用测试集明确统计**具名角色的错误归属数**和默认回退数；提供可检查的人工标注语料与报告，不能只汇报识别率或用“覆盖率高”替代数据。先以零已知误归属为人工回归集门禁；对新收集语料报告混淆结果，不编造全小说准确率。

### 10.2 合成与数据测试

- 用可控假 Provider 验证同声合并、不同声音顺序、所有原文只送一次、指定音色覆盖和普通单音色未变；逐供应商对实际请求体或 SDK 参数做有意义的契约测试，覆盖 OpenAI 自定义声音、腾讯采样率、本地模型、Azure 解码与语言映射等特殊分支。
- 具体音色格式已知/未知/不匹配的 UI 与请求前校验；首块格式、后续块突变、音频帧边界与 `maxBufferSize`；无音频、错误、框架拒收、部分音频后失败均正确终止。
- 首页普通供应商与方案供应商不同，以及普通供应商未配置而方案供应商就绪时，逐一验证语言/音色发现、CHECK_TTS_DATA 与合成入口；切换方案、变更配置和暂停时并发查询不得释放在途 Provider；客户端缓存旧音色名时结果与提示符合第 7.1 节。
- 用确定性交错测试覆盖解析中、等待音频中、段间空隙、队列满、写入中、完成回调竞争、超时、`onDestroy`、新旧请求交错时停止；验证无旧回调、无新段启动、无锁泄漏，系统 callback 均在 synthesis 线程且返回后没有调用。
- 设置并发编辑、开关/切换/删除事务、持久化失败、异常/未来 schema、升级、进程重建、不同仓储实例并发；备份排除与敏感字段无落盘/日志/遥测泄漏；请求中途编辑只影响下一请求。
- UI/无障碍测试覆盖首次配置、缺项、重复名、音色不兼容、创建复制切换删除、关闭重启、预览失败、TalkBack 语义、长文本、大字号及大小窗口；首页两个浮动入口分别验证点击去向、开启/关闭语义、可见状态、导航栏/键盘/通知提示不遮挡及内容末尾可滚动。

### 10.3 工程与实机验证

- 运行 `./gradlew :app:testDebugUnitTest`、`./gradlew assembleDebug`、`./gradlew lintDebug`、`./gradlew assembleRelease`；遵守现有 CI 和发布门禁。报告实际执行结果，不能引用 easyVoice 或旧合并的测试数字冒充本次验证。
- 至少使用两款真实阅读客户端，记录其是否按段、是否保留引号、是否能前后跳转与重复朗读；验证关闭/启用、无引号、跨请求截断、不同角色、停止和跳章。不要未经验证承诺兼容全部阅读器。
